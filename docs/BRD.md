# BRD · 핏플레이스·뮤더 통합 프로젝트

- 작성일: 2026-11-16

## 1. 프로젝트 개요

**itda**는 매장 운영자용 음악 큐레이션 서비스 **muther(track1)**와 일반 사용자용 매장 탐색 서비스 **핏플레이스(track2)**를 연결하는 통합 플랫폼이다.

| 서비스 | 대상 | 제공 내용 |
|---|---|---|
| muther | 매장 운영자 | 날씨·장르·분위기를 고려한 선곡표 생성·확인·적용, YouTube 연계 음악 재생 |
| 핏플레이스 | 일반 사용자 | 조건별 카페·주점 탐색, 메뉴·가격 확인, 찜·리뷰·메뉴 조합 추천, 이벤트 참여 |
| itda | 손님·점주·운영 관리자 | 역할별 진입, 점주 매장 관리 권한 확인, 서비스 간 매장·선곡표 연결 |

## 2. 프로젝트 배경과 문제 정의

### 2-1. 추진 배경

- 기존 뮤더의 음원 데이터와 장르·분위기 태그를 보강하고 동일 평가 자료에서 분류기를 비교한다.
- 매장 운영자 중심의 서비스를 일반 사용자가 매장을 찾고 방문 정보를 확인하는 서비스로 확장한다.
- 공통 로그인·권한과 매장 식별 정보를 이용해 점주가 적용한 선곡표를 손님용 매장 정보에 연결한다.

### 2-2. 해결하려는 문제

이 프로젝트는 매장 운영자의 선곡 작업과 일반 사용자의 방문 결정 과정에서 발생하는 다음 불편을 해결 대상으로 삼는다. 아래 내용은 기획에서 정의한 이용 상황이며, 사용자 조사로 확인한 빈도나 효과를 의미하지 않는다.

| 대상 | 불편 |
| --- | --- |
| 매장 운영자 | 날씨와 매장 분위기를 고려해 곡을 직접 찾고, 추천된 곡이 의도와 다르면 선곡표를 다시 조정해야 한다. |
| 매장 운영자 | 장르·분위기 태그가 부족하거나 부정확하면 조건을 선택해도 원하는 곡을 고르기 어렵다. |
| 일반 사용자 | 가까운 매장을 찾은 뒤에도 업종, 영업 여부, 예산, 메뉴와 위치를 매장별로 다시 확인해야 한다. |
| 일반 사용자 | 거리만 가깝거나 가격만 맞는 결과로는 오늘의 날씨·분위기·방문 목적에 맞는 곳인지 판단하기 어렵다. |
| 일반 사용자 | 메뉴별 가격만으로는 여러 명이 함께 주문할 조합과 총예산을 판단하기 어렵다. |
| 일반 사용자 | 매장을 바꾸어 비교할 때마다 메뉴를 고르고 비용을 다시 계산해야 한다. |
| 일반 사용자 | 관심 매장을 찾았어도 바로 방문하지 않으면 나중에 같은 조건으로 다시 검색해야 한다. |
| 일반 사용자 | 매장 소개만으로 판단하기 어려운 부분은 다른 사용자의 경험과 함께 살펴볼 필요가 있다. |

### 5-1. In Scope

| 범위 | 내용 |
|---|---|
| track1 | 음악 데이터 적재, 추천·YouTube 재생, 피드백 적재 |
| track1 | 오디오 기반 장르·분위기 자동 태깅과 모델 비교 |
| track2 | 위치·지역·조건별 탐색, 목록·지도·상세·메뉴 조회 |
| track2 | 고정 초기 가중치를 사용하는 Two-Tower 개인화 순위, 사용자 취향 벡터 갱신, Gemini 추천 이유 안내 |
| track2 | 찜·리뷰·메뉴 조합 추천 |

### 5-2. Out Scope

다음 기능은 이번 제공 범위에서 제외한다. 후속 작업은 11번에 정리한다.

| 영역 | 제외하는 기능 | 포함 범위와의 구분 |
|---|---|---|
| 실시간 재생 동기화 | 뮤더와 핏플레이스 간 현재 재생 곡, 재생 위치, 재생·일시 정지 상태의 실시간 동기화 | 같은 매장에 승인 선곡표를 연결하고 표시하는 기능은 포함한다. |
| 학습된 매장 추천 모델 | Two-Tower 가중치 학습·배포와 사용자 행동에 따른 모델 자동 재학습 | 고정 초기 가중치 기반 순위 계산, 사용자 취향 벡터 갱신, Gemini 안내는 포함한다. 음악 분류 모델의 학습·평가도 포함한다. |
| AWS 자원 종료·삭제 | Lifecycle을 통한 실제 AWS 자원 종료와 삭제 | 인프라 구성·배포·상태 검사와 로컬에서 검증한 Lifecycle 로직은 포함한다. |

통합이 끝나지 않았거나 결과를 검증하지 않았다는 이유만으로 제외 범위로 분류하지 않는다. 운영 매장 연결, 화면 통합과 포함 기능의 검증은 업무 범위에 유지한다.

## 6. 목표 업무 흐름

| 대상 | 흐름 |
|---|---|
| 점주 음악 운영 | 음악 데이터 준비 → 추천 조건 설정 → 선곡표 확인·승인·적용 → YouTube 연계 재생·피드백 |
| 손님 매장 탐색 | 지역·위치·조건 설정 → 목록·지도·추천 안내 → 상세·메뉴 확인 → 찜·리뷰·메뉴 조합 이용 |
| 이벤트 | 점주가 시간·혜택·수량 설정 → 손님 참여 의사·QR 발급 → 현장 인증 → 재고 차감·활동 기록 |
| 정보 검수 | 손님 폐업 제보 → 노출 관리·관리자 검수 → 폐업 확인 시 숨김 또는 정상 영업 확인 시 복구 |
| 서비스 연결 | 점주 관리 권한 승인 → 점주 작업공간과 공개 매장 연결 → 적용 선곡표를 손님 상세에서 조회 |

## 7. 주요 비즈니스 요구사항

- 손님과 점주는 공통 진입을 사용하고 관리자는 별도 로그인 경로를 사용한다. 점주는 관리 권한을 확인한 본인 매장을 관리한다.
- 사용자는 지역·날씨·예산 등의 조건과 매장·메뉴 정보를 이용해 방문할 매장을 비교한다. Gemini는 제공된 후보와 상황을 바탕으로 추천 이유를 안내한다.
- 찜·리뷰·메뉴 조합 추천은 MVP에 포함한다. 메뉴 가격 조회와 메뉴 조합 계산을 구분한다.
- 이벤트 참여 의사를 표시할 때 재고를 유지하고, 현장 QR 인증 시 1개 차감한다. 동일 계정·동일 이벤트의 인증은 하루 1회로 제한한다.
- 제보와 검수에 따라 매장 노출을 관리한다. 찜한 매장 이벤트 시작과 참여 예정 이벤트의 조기 종료·재고 소진을 알린다.
- 공통 `venue_id`로 같은 매장을 연결하고 승인·적용 선곡표를 표시한다. 승인 선곡표가 없는 파트너 매장에는 날씨 기반 음악 테마 안내를 설계한다. 운영 연결은 별도 검증한다.
- 데이터 누락이나 연결 장애가 발생하면 사용자가 상태를 알 수 있도록 한다.

## 8. 데이터 관리 원칙

- 실제 데이터 처리와 합성 테스트 데이터를 구분한다. 발표에서 제시한 테스트 매장 조회를 전체 운영 데이터 통합으로 해석하지 않는다.
- 매장 카탈로그 분석용 처리와 온라인 추천 경로를 구분한다. 운영 데이터 인수 후 통합 결과는 별도 기록한다.
- 분할 도착한 날씨 자료를 보존해 최신 완성 회차를 선택하고 유효한 예보만 추천에 사용한다.
- 공통 매장 ID와 점주 관리 권한을 기준으로 선곡표를 연결한다.
- 사용자 행동에 따른 취향 벡터 갱신과 모델 가중치 학습을 구분한다.

## 10. 운영 자원과 제약

- 발표의 인프라는 AWS 5계정·5VPC·16EC2·3AZ 설계다. CloudFront·ALB로 진입하고 업무 서버는 사설망에 배치한다.
- Terraform은 자원 구성, Ansible은 호스트 설정·배포, Lifecycle 실행기는 종료·보존·재개를 담당한다. 실제 AWS 종료·삭제 연동은 미완료다.
- 모델 추론은 Gateway·Tailscale을 거쳐 별도 PC의 API에 연결하는 설계다.
- 사용자 벡터는 프로세스 메모리 기반이며 재시작 후 지속성과 추천 품질은 별도 검증 대상이다.
- 승인 선곡표의 로컬 조회와 운영 매장 연결을 구분한다.
