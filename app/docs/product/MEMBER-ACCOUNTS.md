# 회원·복구·마이페이지 실행 계약

이 문서는 공개 가능한 제품·기술 계약입니다. 내부 대화 원문, 담당자 연락처, 운영 자격증명, 실제 회원 데이터와 실행 보고서는 포함하지 않습니다. 2026-11-06 추가 승인 정책을 적용하며 이전 이메일 필수 가입 흐름을 대체합니다.

## 가입과 사용자 화면

- `/signup`: 아이디·비밀번호·선택 별명과 약관/안내/연령 확인. 이메일은 선택 동의한 경우에만 전송·저장·발송합니다. 이메일 미등록·미확인 상태에도 계정을 즉시 생성하고 일반 로그인을 허용합니다.
- 아이디는 ASCII 영문·숫자·밑줄 4~20자입니다. 소문자로 저장하며 로그인과 중복 확인은 대소문자를 구분하지 않습니다. `auth_user.lower(username)` 고유 인덱스가 동시 가입도 방어합니다. 가입 후 변경 API는 없습니다.
- 신규 비밀번호는 공백 없이 ASCII 영문·숫자·특수문자 8~20자이며 대문자 1개 이상과 특수문자 2개 이상이 필요합니다. Django의 유사 정보·흔한 비밀번호 검증과 Argon2id 해시를 사용합니다. 같은 특수문자의 반복도 개수에 포함합니다. 소문자·숫자 자체는 필수가 아닙니다. 가입·변경·재설정에 동일하게 적용하며 기존 비밀번호로 로그인·현재 비밀번호를 확인하는 절차는 유지합니다.
- 별명은 선택 입력, 2~10자이며 한글·ASCII 영문·숫자만 받습니다. 공백·특수문자는 허용하지 않으며 각 문자 종류가 모두 필수인 것은 아닙니다. NFKC 정규화·casefold 키로 중복을 막습니다. 비어 있으면 `회원0000`~`회원9999`를 무작위로 만들고 고유 제약 충돌 시 제한된 횟수로 재시도합니다. 공간이 부족하면 직접 입력을 안내하며 자릿수를 임의 확장하지 않습니다.
- 이용약관 동의, 기본정보 처리 안내 확인, 만 14세 이상 확인은 가입 조건입니다. 체크는 기본 해제이며 기본정보 안내 확인을 법적 수집 동의로 표시하지 않습니다. 생년월일·실명은 수집하지 않습니다.
- `/login`: USER와 기존 ADMIN을 지원합니다. USER 세션은 기본 8시간, 로그인 유지 선택 시 7일입니다. 역할은 서버가 결정하며 USER 가입 요청으로 관리자 권한을 부여할 수 없습니다.
- `/mypage`: 별명 변경, 마스킹된 확인 이메일, 복구 주소 등록/변경/삭제, 비밀번호 변경, 저장 선곡표 조회/삭제, 회원탈퇴를 제공합니다. 중요 변경은 현재 비밀번호를 다시 확인합니다.

기본 추천은 비회원에게 계속 제공합니다. 회원의 선곡 소유자는 별도 UUID이며 익명 기록을 계정에 자동 합치지 않습니다. 로그인 후 만든 본인 선곡표만 명시적으로 저장할 수 있습니다. ‘이 선곡표 승인’과 ‘내 선곡표에 저장’은 별개의 행동입니다. 저장된 결과는 사용자별 불변 스냅샷이며 다른 사용자에게 조회·삭제 권한을 주지 않습니다.

## 이메일 확인과 복구

확인 이메일 한 개당 계정 한 개입니다. 주소 비교는 도메인을 IDNA/소문자로 정리하고 local part는 보존합니다. 제공자별 점·플러스 별칭은 자동 병합하지 않습니다. 이 비교 규칙을 확인·중복·복구 조회에 동일하게 사용합니다.

복구 이메일 확인은 6자리 코드, 5분, 최대 실패 5회, 재발송 간격 60초입니다. 회원 프로필을 잠그고 실패 횟수를 커밋한 뒤 오류를 응답하여 실패 횟수가 롤백되지 않게 합니다. 새 주소를 확인할 때까지 기존 확인 주소를 유지하고, 확인 완료 후 새 주소 반영·이전 복구 토큰 무효화·기존 주소 보안 안내를 같은 트랜잭션에서 처리합니다. 새 코드 발급은 이전 코드를 무효화합니다.

아이디 안내와 비밀번호 재설정은 서로 다른 목적의 10분 일회용 토큰입니다. 등록 여부와 관계없이 같은 요청 응답을 제공하며 실제 발송은 SMTP outbox로 분리합니다. 링크의 토큰은 URL fragment에 넣고 화면이 읽은 즉시 주소에서 제거합니다. GET이나 메일 링크 스캐너는 토큰을 소비하지 않습니다. 명시적 확인 POST가 토큰을 소비합니다. 아이디 안내는 아이디만 반환하며 로그인·비밀번호 변경 권한을 주지 않습니다. 재설정은 기존 세션과 미사용 복구 토큰을 무효화하고 정상 로그인을 요구합니다.

이메일 변경·삭제에는 현재 비밀번호가 필요합니다. 선택 동의 철회는 주소와 대기 메일을 지우고 복구 권한을 회수합니다. 이메일이 없고 로그인 수단도 분실한 계정을 이름이나 새 이메일만으로 넘겨주지 않습니다. 일반 회원 복구 API는 관리자 계정에 적용되지 않습니다.

주소는 키 버전이 포함된 AES-256-GCM 암호문으로 저장합니다. 별도의 32바이트 키로 용도를 구분한 HMAC-SHA-256 조회값을 만들며, 코드/링크 원문은 토큰 테이블에 저장하지 않습니다. 발송 outbox의 주소·본문·원문 코드/링크도 암호화합니다. 두 Control 호스트는 같은 DB와 키 설정을 사용합니다. 조회 키를 바꾸면 기존 인덱스·토큰이 영향을 받으므로 운영 데이터 변환을 별도 설계해야 합니다. 암호화 키 교체 시 이전 복호화 키를 유지하고 새 active 버전으로 저장할 수 있습니다.

## 관리자 패스키

기존 비밀번호/OIDC 검증 후 `/admin/passkey`에서 WebAuthn 추가 인증을 요구합니다. 서명 검증, 고정 RP ID/origin, 무작위 challenge·만료·세션 바인딩·일회 사용·user verification을 서버가 확인합니다. 추가 인증 전에는 관리자 API를 거부합니다. 운영 모드에서는 패스키 요구를 환경변수로 끌 수 없습니다. 라이브러리는 `webauthn==3.0.1`로 고정합니다.

최초 등록에는 기본 인증과 운영자가 별도 본인 확인 후 발급한 일회용 등록권이 모두 필요합니다. SSO 계정의 앱 내부 username은 issuer/sub 해시로 생성된 값이므로 해당 앱 계정을 확인해 발급합니다.

```sh
python -m backend.manage issue_passkey_enrollment ADMIN_USERNAME
# 분실 후 운영자의 신원 확인·영향 확인을 마친 명시적 교체:
python -m backend.manage issue_passkey_enrollment ADMIN_USERNAME --replace-lost-keys
```

출력은 등록권 비밀값입니다. 공유 터미널 녹화·명령 로그·보고서·Git에 남기지 않습니다. 분실 교체는 기존 패스키와 앱 세션을 회수합니다. 이메일 복구로 패스키를 해제하지 않습니다. 마지막 관리자 분실 시의 담당자·권한 증명 절차는 운영 전에 확정해야 합니다. 실제 IdP/Elastic의 직접 접속과 세션 정책은 각 서비스에서 별도로 강제해야 하며, Django의 추가 인증만으로 외부 대시보드의 MFA가 설정됐다고 표시하지 않습니다.

## 실행과 운영 입력

로컬 Compose는 `settings_docker_local`, 임의 생성 키, Mailpit과 검증용 정책 문구를 사용합니다. 기존 `.env` 값은 보존하면서 없는 로컬 키만 추가합니다.

```sh
python3 docker/init_dev_env.py
docker compose build api frontend
# 기존 DB migration은 영향 검토 후 별도 실행합니다.
docker compose --profile workers up -d api frontend mailpit account-mail-worker
```

새 격리 데이터베이스에서 검증하려면 저장소 루트의 다음 명령을 사용합니다. 기존 Compose 서비스와 데이터는 대상이 아닙니다.

```sh
docker build -t mlo-p4-frontend:dev -f app/docker/frontend.Dockerfile app
make app-images member-check app-predeploy
```

검사는 Git 후보 앱 파일만 복사하고 현재 소스 revision의 운영 이미지에서 React 빌드를 가져와 새 PostgreSQL/메일/브라우저 프로젝트를 만듭니다. Vite 없이 Django가 제공하는 실제 빌드 화면에서 회귀·동시성·SMTP·Chromium 흐름을 실행합니다. 물리 패스키 대신 Chromium 가상 인증기를 사용하며 실제 기기 등록 성공을 의미하지 않습니다. 생성한 컨테이너·볼륨·네트워크만 종료·정리합니다. 보고서는 Git 제외 경로에 보관합니다. 이후 앱 변경은 운영 이미지와 회원 수용을 함께 다시 검증합니다.

운영에서는 `MEMBER_POLICIES_READY=0`이 기본이며 최종 정책 게시 전 가입을 열지 않습니다. `backend/.env.example`과 보호된 런타임 secret 파일을 통해 다음 입력을 주입합니다.

- `MEMBER_POLICY_VERSION`, `MEMBER_POLICY_DOCUMENTS`의 terms/privacy_notice/email 전문과 `MEMBER_POLICIES_READY`.
- `MEMBER_EMAIL_KEYS` JSON keyring, `MEMBER_ACTIVE_EMAIL_KEY`, 별개의 `MEMBER_LOOKUP_KEY`. 키 값은 각각 base64 32바이트이며 Git·이미지에 넣지 않습니다.
- `MEMBER_PUBLIC_ORIGIN`, `ADMIN_PASSKEY_RP_ID`, `ADMIN_PASSKEY_ORIGIN`. 실제 서비스 origin은 HTTPS이며 임의 Host 헤더로 만들지 않습니다.
- SMTP 호스트/포트/계정/비밀, 발신 주소, STARTTLS 또는 TLS 중 하나. 발송 연결 타임아웃은 10초입니다.
- `MEMBER_MAIL_LIMIT_HOUR`, `MEMBER_RECOVERY_IP_LIMIT_HOUR`, `MEMBER_LOGIN_LIMIT_HOUR`, `MEMBER_PUBLIC_LIMIT_HOUR`, `MEMBER_SECURITY_MAIL_SECONDS`. 운영 제한·보안 안내 큐 보유시간은 명시적으로 정합니다. 로컬 검증의 10/30/100회 및 1시간 예시는 운영 승인값이 아닙니다.

`deliver_account_mail`은 공유 DB lease로 발송을 담당하고 사용/만료 토큰·만료 큐를 정리합니다. SMTP 오류는 범주만 기록하고 지수 지연으로 재시도합니다. 성공 시 payload를 삭제합니다. SMTP가 수신을 승인한 직후 연결이 끊기면 성공 여부가 불명확하므로 정확히 한 번 발송을 보장하지 않습니다. 재시도에 같은 Message-ID를 사용하며 중복 수신 때도 토큰 권한은 일회용입니다. 이미 SMTP로 전송 중인 메일은 철회로 회수할 수 없습니다.

회원탈퇴는 현재 SQL의 계정·프로필·동의 기록·토큰/대기 메일·세션·저장 이력·회원 소유 추천/피드백 데이터를 정리합니다. Kafka/검색/별도 로그·백업·메일 사업자 기록과 복원 시 삭제 재적용은 운영 파기 절차에 포함해야 합니다. 모든 저장소의 파기가 Django DB 삭제만으로 완료되었다고 표시하지 않습니다. 실제 운영자/연락처, SMTP 제공자/위탁·이전 조건, 동의/운영 로그와 백업 보유·파기 기준, 복구 문의 절차를 운영 전에 확정합니다.

## API

| 경로 | 기능 |
|---|---|
| GET `/api/accounts/policy` | 게시 문서·버전·로컬 검증 여부 |
| POST `/api/accounts/availability` | 아이디 형식·중복 확인 |
| POST `/api/accounts/signup` | 계정 생성, 선택 이메일 확인 요청 |
| POST `/api/auth/login`, `/api/auth/logout` | 공통 USER/ADMIN 세션 |
| GET `/api/auth/me` | 서버 역할·CSRF·관리자 추가 인증 상태 |
| GET/PATCH `/api/me/profile` | 본인 정보·별명 변경 |
| POST/DELETE `/api/me/email` | 복구 이메일 등록·교체/철회 |
| POST `/api/me/email/verify` | 확인 코드 검증 |
| POST `/api/me/password` | 현재 비밀번호 확인 후 변경 |
| POST `/api/accounts/recovery` | 존재 여부를 감춘 복구 요청 |
| POST `/api/accounts/recovery/complete` | 목적에 맞는 일회용 토큰 소비 |
| GET/POST `/api/me/playlists` | 본인 저장 이력/명시적 저장 |
| GET/DELETE `/api/me/playlists/:id` | 본인 저장 스냅샷 조회·삭제 |
| POST `/api/me/withdraw` | 재확인·문구 확인 후 탈퇴 |
| POST `/api/admin/passkeys/options`, `/verify` | 관리자 WebAuthn 단계 |

모든 상태 변경은 CSRF를 검증합니다. 동의 증적에는 문서 버전·종류·해시·선택·시각을 기록하고 이를 위해 별도 IP·기기정보를 수집하지 않습니다. 요청 제한에는 원문 이메일/IP 대신 HMAC 식별값을 사용합니다.


## 중앙 플랫폼의 계정 진입점

중앙 플랫폼의 로컬 MVP가 활성인 환경에서는 회원 계정을 한곳에서 관리합니다. 사용자·사업자가 동일한 공통 계정으로 로그인하며, 서버가 현재 활성 이용 유형을 확인해 이동 경로를 정합니다. 두 유형 모두 활성이라면 로그인 후 선택하며 선택 문맥은 세션별입니다.

| 기능 | 화면 경로 |
| --- | --- |
| 공통 로그인 | `/platform/login` |
| 공통 회원가입 | `/platform/signup` |
| 아이디 찾기·비밀번호 재설정 | `/platform/account/recovery` |
| 계정·보안·개인 저장 자료 | `/platform/account` |
| 매장 운영 | `/platform/business` |
| 플랫폼 관리자 | `/platform/admin/login` → `/platform/admin` |

중앙 플랫폼 활성 여부는 공통 `/api/auth/me`의 `platform_enabled`로 확인합니다. 활성 환경의 기존 `/login`, `/signup`, `/account/recovery`, `/mypage` 진입은 위 화면으로 연결하고 복구 fragment를 보존합니다. 독립 서비스 환경의 기존 화면은 유지합니다. 새 복구 메일도 중앙 경로와 일회용 fragment를 사용합니다.

계정 API의 기준 명세는 `backend/workspaces/contract.json`이며 `/api/platform/v1` 아래에 있습니다. 선택 응답 필드 `Account.email_challenge_id`는 인증된 본인의 유효한 대기 이메일 확인 요청 UUID입니다. 코드 검증을 대신하는 비밀값이 아니며 서버가 계정·만료·코드·시도 횟수를 검증합니다. 복구 요청은 주소 존재 여부와 관계없이 같은 응답을 반환하고 주소별 60초 간격을 유지합니다.

사업자 가입 팝업은 공통 가입 → 국세청 사업자 정보 확인 → 별도 매장 관리권한 심사 → 승인·권한 부여를 설명합니다. 현재 로컬 MVP는 합성 정보만 사용하며 LIVE 국세청 조회는 하지 않습니다. 기존 매장의 직원은 소유자 초대를 수락해 참여합니다. 확인/심사 상태마다 다음 행동을 안내하며 사업자 정보 일치만으로 매장 권한을 부여하지 않습니다.

관리자 1차 로그인과 추가 인증 완료를 구분합니다. 추가 인증 전에는 관리자 업무를 열지 않으며 공개 회원가입으로 관리자 권한을 만들지 않습니다. 로컬 패스키 ceremony 인수는 현재 보류되어 있고 기존 인증 요구는 유지합니다.

플랫폼 공통 푸터의 이용약관(`/platform/terms`), 개인정보 처리방침(`/platform/privacy`), 문의(`/platform/privacy-contact`)는 로그인 없이 볼 수 있습니다. 현재 로컬 문서는 시연 검토본이며 운영 주체·보유/파기·공식 문의처의 확정과 운영 게시를 대신하지 않습니다. 미확정 문의처를 임의의 주소로 표시하지 않습니다.

## 2026-11-06 입력 정책 v0.8

위 규칙은 공통 플랫폼 가입/계정 변경/복구와 독립 회원 API에 동일하게 적용합니다. 기존 회원 별명·해시의 일괄 변환이나 DB migration은 수행하지 않습니다. 별명을 새로 저장할 때는 새 규칙을 확인합니다. API 응답의 기존 별명을 10자로 잘라내지 않습니다.

가입 폼의 선택 이메일·동의는 가입 후 확인 코드 발송을 요청합니다. `/platform/account`의 계정·보안 관리 → 복구 이메일 관리에서 6자리 코드와 ‘이메일 확인’ 버튼으로 완료합니다. 가입 전 인증 버튼/이메일 필수 가입은 현재 계약에 포함하지 않습니다. 코드는 5분·5회, 재발송 60초, 확인 이메일당 계정 하나 규칙을 유지합니다.
